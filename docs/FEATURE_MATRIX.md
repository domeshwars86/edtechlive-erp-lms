# Feature Matrix

**Legend:** P0 essential foundation; P1 first commercially usable release; P2 advanced/premium; Future expansion. Status reflects this repository only.

| Feature | Priority | Purpose / roles | Inputs → outputs | Data / API / screens | Permissions, validation and failure handling | Acceptance / test focus | Complexity | Status |
|---|---|---|---|---|---|---|---|---|
| Public website | P0 | Explain product; all visitors | Route/content → clear product overview | Web pages; public API not required | Public content; responsive and route fallback | All public routes navigate; viewport and keyboard review | M | Complete and tested (frontend gate) |
| Course discovery preview | P0 | Show learning catalog; visitors/students | Search, level → filtered sample cards | Future Course, Category, Educator; GET `/api/v1/courses`; course page | Published course visibility; validate query/filter; empty state | Search/filter/empty state | M | Implemented with clearly labelled sample data |
| Enquiry | P0 | Gather prospective user needs | Contact fields/consent → success/error | Future Enquiry; POST `/api/v1/enquiries`; contact form | Validate name/email/category/message and consent; backend errors shown | Invalid entries blocked; API errors recoverable | M | Frontend-only preview; no transmission |
| Identity and organization context | P0 | Secure user access across tenants | Credentials, MFA, membership → authenticated context | User, Org, Membership; `/auth/*`, `/api/v1/me`, `/api/v1/organizations`; auth/select org UI | Policies, role checks, rate limiting; generic auth errors | Current-user auth and organization membership isolation covered; registration/login/recovery pending | L | Partially implemented: Sanctum guard and membership-scoped list; auth flows/policies pending |
| Organization/academic masters | P0 | Configure academic operations; admins and management | Session/class/subject inputs → organization records | Organization, Session, Class, Section, Subject; `/organizations/{id}/academic-sessions`, `/classes`, `/subjects` | Active membership required; writes restricted to admin, management, or independent educator; unique names/codes and valid dates | Create/list/update, session selection, role restriction, tenant isolation | L | Partially implemented: API and admin dashboard create/list/archive flows for sessions, classes, sections, subjects; PostgreSQL validation and richer edit workflows remain |
| People and roles | P0 | Maintain learners/staff; admins | Profile inputs → organization roster records | Student, Teacher, TeachingAssignment, Membership; `/organizations/{id}/students`, `/teachers`, `/teaching-assignments` | Admin/management/independent-educator role; unique admission/employee IDs; tenant-scoped class placement | Create/search/update status, assignment consistency, tenant isolation, restricted roster reads | L | Partially implemented: tenant-scoped student/teacher profiles and subject/section teacher assignment APIs/admin screens; account invitations and guardian linkage remain |
| Attendance and schedule | P1 | Coordinate teaching and participation | Date, section, status, weekly slot → register and timetable | AttendanceRecord, TimetableEntry; `/organizations/{id}/attendance`, `/timetable` | Verified admin/management/independent educator access; active student placement; session dates; assigned teacher required for teacher-owned timetable slots; duplicate upsert and schedule overlap checks | Batch mark/update; tenant isolation; section/teacher/room conflict detection | M/L | Partially implemented: admin attendance and timetable screens use persistent APIs; schedule teacher must be assigned to the matching section/subject/session; teacher marking and reports remain |
| Courses, lessons, materials | P0 | Deliver structured learning; teachers/students | Course content/files → accessible lessons | Course, Module, Lesson, Asset; `/courses`, `/lessons` | Teacher ownership, private media, upload rules | Authoring, access, file permissions | L | Preview cards only; backend not started |
| Live and management meetings | P1 | Connect classes and staff | Time, organizer, attendees, link → schedule/detail | Meeting, Participant; `/meetings`; Meet provider/manual URL | Authorized participants, valid URL/time; provider failure permits manual entry | Correct visibility and link behavior | M | Not started |
| Assignments and exams | P1 | Practice and assess learning | Prompt, due date, questions/submission → feedback/results | Assignment, Submission, Exam, Question, Attempt; `/assignments`, `/exams` | Teacher class access; student own submission; transactional grading | Attempts, duplicates, result accuracy | L | Not started |
| Reports and notifications | P1 | Surface academic status and reminders | Scoped filters/events → report/alerts | Report, Notification; `/reports`, `/notifications` | Tenant visibility, safe notification payload, delivery status | Scope and delivery failure/retry | M/L | Not started |
| Fee records/payment | P1 | Track finance and future collection | Invoice/manual receipt/sandbox event → ledger/status | Fee, Invoice, Payment, Webhook; `/fees`, `/payments` | Finance role; idempotency; sandbox only initially | Webhook retry and amount/state validation | L | Not started |
| AI assistance | P2 | Optional teaching/learning help | Prompt/authorized context → draft explanation/questions | AI usage/config; `/ai/*` | Rate/cost limits, moderation, no auto-grading, provider failure fallback | Safety, authorization and quota behavior | L | Not started |
| Mobile apps | P1 after web | Essential mobile workflows; teachers/students/admin | API actions → synced app views | Shared API, React Native clients | API policies remain authoritative | Android/iOS workflow/device tests | L | Not started |
| Subscriptions and entitlements | Future/P2 | Monetize later | Plan and usage → entitlements/billing | Plan, Entitlement, Usage, Subscription | Disabled until commercial approval/configuration | Feature limits and billing sandbox | L | Not started |

Complexity: S small, M medium, L large. Only routes listed as implemented in `docs/API_SPECIFICATION.md` are operational. Each feature's detailed failure and acceptance criteria are refined before implementation.

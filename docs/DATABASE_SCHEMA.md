# Database Schema Direction

**Status:** Identity, organization, membership, invitation, academic session/class/section/subject, exams, students/teachers/guardian links, courses/modules/lessons/enrollments/progress/assets, course-scoped question banks and bank questions, assignments/submissions, quizzes/attempts, fees/receipts, expenses, bank statement reconciliation, teaching assignments, attendance, timetable, meetings, announcements, notifications, enquiries and platform audit events have implemented tables/models/migrations. The migration suite passed on SQLite and a disposable PostgreSQL 17 instance. PostgreSQL 16 hosted CI and production database/deployment validation remain pending.

## Core entities

- `users`: identity and verified contact fields plus nullable `preferred_organization_id`; the API restores this only while the user has an active membership and the organization is active. Organization deletion clears the preference. Never duplicate authentication secrets in domain records.
- `organizations`: tenant, type, status, locale/timezone and settings.
- `memberships`: user, organization, role/status, invitation/activation timestamps; unique active user/organization/role policy.
- `organization_invitations`: organization, normalized email, limited role, hashed one-time token, inviter, expiry, and acceptance audit fields. Raw invitation tokens exist only in the mail link.
- `contact_enquiries`: public prospective-user submissions with contact details, consent timestamp, workflow status, optional notification timestamp, and latest response time/operator. This table is not tenant-owned; reads and reply actions are restricted to verified allowlisted platform operators, and reply text is not stored on the enquiry record.
- `fee_records`, `fee_payments`: tenant-owned INR receivables for active students and staff-entered partial/final receipts. Each receipt stores the staff user, method, optional reference, and received timestamp; this is a manual ledger, not a gateway transaction.
- `bank_statements`, `bank_statement_lines`: tenant-owned CSV-imported statement periods, account labels, opening/closing balances, a unique-per-tenant content fingerprint and transaction lines. Statement lines may be linked one-to-one to a same-tenant fee receipt or expense; matched ledger IDs are unique across statements. No account number, bank credential, or raw uploaded statement is retained.
- `meetings`: tenant-owned one-time class or management meeting with optional section/session or published course scope, HTTPS meeting URL, start/end time, creator, and scheduled/cancelled state. No provider credentials or participant secrets are stored.
- `notifications`: Laravel database notifications addressed to individual users; payloads carry organization and event identifiers for fee issue/receipt and meeting scheduling. Reads and read receipts are restricted to the recipient and active organization membership.
- Organization membership roles are currently represented by a backed enum and membership records; dedicated `roles`, `permissions` and membership-role assignment tables are planned, not implemented.
- `academic_sessions`, `academic_classes`, `academic_sections`, `academic_batches`, `subjects`: organization-owned academic structure. Batches are unique by organization, academic session, class and name; optional sections must match the selected class/session. Batch search and filters are paginated; records can be activated/deactivated without deleting academic history.
- `students`, `teachers`: organization-owned roster profiles with optional class placement and organization-scoped admission/employee identifiers. Teacher profiles link to one user account; student profiles can link to one user account. `student_guardians` links a guardian account to explicitly authorized student profiles, with relationship, primary-contact and inviter metadata.
- `organization_invitation_students`: tenant-scoped selected student profiles attached to parent invitations; links are created only after successful invitation acceptance.
- `teaching_assignments`: tenant-owned teacher/subject/section/session links; timetable entries require the matching assignment when a teacher is set.
- `attendance_records`, `timetable_entries`: class/session/date/user-scoped academic activity. Attendance has one mark per student/section/date and records the marking user. Timetable entries contain weekday/time, room, optional assigned teacher, and optional secure meeting URL.
- `courses`, `course_modules`, `course_enrollments`, `course_lessons`, `course_lesson_progress`: course drafts/publication, ordered tenant-scoped modules, active student enrollment, ordered lessons optionally grouped by module, and per-student completion timestamps for published lessons. `course_assignments` and `assignment_submissions`: published prompts, due dates, student text responses, numeric grades and instructor feedback. `course_quizzes` stores optional open/close timestamps, time/attempt limits, a proportional negative-marking rate and optional pass percentage. `course_question_banks` and `course_question_bank_questions` store editable course-scoped reusable questions; `quiz_questions.question_bank_question_id` records optional source provenance while quiz content remains an independent snapshot. `quiz_questions` stores objective option sets and private correct answers or teacher-reviewed written prompts. `quiz_attempts` stores bounded submissions, `review_status`, per-question `manual_grades`, and objective/server-updated scores. `course_assets` stores tenant/course metadata and opaque private storage keys; downloads go through an authorized API route. `academic_exams`, `academic_exam_papers`, `academic_exam_paper_sections`, `academic_exam_results`, and `academic_exam_section_results` store session schedules, section/subject papers, optional ordered board-style paper parts with mark maximums, total and per-part scores, absent/excused outcomes, teacher audit, and family-visible published results. Exam series remain planned.
- `course_question_banks`, `course_question_bank_questions`: reusable objective or written-response questions scoped to a course and its authorized editor/teacher; quiz imports keep a snapshot and provenance link so later bank changes cannot rewrite an assessment. Bank question content is not exposed to students. `quiz_attempts.manual_grades` stores per-question points, feedback and reviewer metadata; `review_status` tracks not-required, pending, partial or graded attempts. Aggregate score averages omit pending and partially reviewed attempts.
- Assessment data currently uses `course_assignments`, `assignment_submissions`, `course_quizzes`, `quiz_questions`, `quiz_attempts`, `academic_exams`, `academic_exam_papers`, paper sections and section results; a generalized exam-attempt model and exam series are planned.
- `meetings` supports organization-scoped meeting links; provider provisioning and a participant table are not implemented.
- `notifications`, `announcements`, and `platform_audit_events` are implemented. Audit events currently cover allowlisted platform organization status changes; a broader audit log is planned.
- Finance currently uses `fee_records`, `fee_payments`, `finance_expenses`, `bank_statements` and `bank_statement_lines`. Fee categories, invoicing and payment webhook tables are planned; the current ledger does not initiate payments.
- AI usage records/provider configuration references are planned; secrets must live outside the database and source.

The implemented schema uses `organizations` and `organization_memberships`, indexed by organization/user/status with a unique organization/user membership. Tenant-owned domain tables carry organization ownership and tenant-aware validation/index constraints. Attendance, enrollment and course-progress reports aggregate existing records and require no separate materialized table. Migrations and API behavior pass on SQLite and disposable PostgreSQL 17; hosted PostgreSQL 16 CI and production verification remain open. Role, organization type and membership status use PHP backed enums.

## Modeling rules

Every tenant-owned entity carries a non-null organization key and has tenant-aware foreign keys/unique constraints where PostgreSQL supports the design. Use UTC timestamps with organization timezone for display. Index organization plus common filter/sort keys. Define soft-delete vs. retention carefully; it is not a substitute for deletion policies. Store file metadata and private storage identifiers, not public permanent URLs. Use transactions for enrollment, assessment finalization and payment state changes. Webhook idempotency keys are unique.

## Open decisions

Dedicated permission modeling, enrollment lifecycle, academic calendar flexibility, attendance correction, exam scoring model, child-data retention, financial accounting, partitioning thresholds and data residency require discovery before the schema is considered production-ready.
